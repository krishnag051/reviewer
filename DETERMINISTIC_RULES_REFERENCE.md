# Deterministic Rules Reference

Written 2026-10-08, directly against the real, current codebase (`agent-making/agent/pipeline/fields.py`, `rules/rules.json`) — not from memory. This is a **permanent, standing** reference, meant to answer "what does this rule actually check, and how fragile is it" without re-deriving it from scratch every round.

**Scope of this file**: every rule with `check_type: "deterministic"` in `rules.json` — **90 active rules**, of which **84 have a real Python checker function** registered in `pipeline/fields.py::DET_CHECKS`, and **6 are labeled deterministic but have no checker built at all**, so they escalate to the AI judgment layer on every single run (listed separately below; they are documented in `JUDGMENT_RULES_REFERENCE.md` instead, since that is the layer that actually decides them).

## How to read the main table

- **Function** is the exact, real `pipeline/fields.py` function that implements the rule. Several rule_ids intentionally share one function (e.g. `EMB-01`/`ANT-01`/`EMP-01` all route through `_check_EMP01`/`_check_HF02`-family functions) — this is deliberate code reuse across payor-specific rules with identical logic, not a bug.
- **Docstring's own first line** is pulled directly from that function's own docstring (first paragraph, truncated to ~220 characters) — it is the function's own, real, current description of its data source and mechanism, not a paraphrase. Where it's empty, the function has no docstring (rare, flagged as a gap below).
- A rule's own `params` (if any) come from `rules.json` and are **not** separately listed here — read `rules.json` directly for the exact live thresholds (e.g. HRS-11's per-payor hour caps), since those can change without a code change.

## Shared, cross-cutting mechanisms every deterministic checker relies on

1. **`find_labeled_sections(text, label)`** — the shared primitive for "find every real occurrence of a `Label:` field, in document order, bounded by the next known section label or the label's own next occurrence." Returns `[]` only when the label never appears at all; a non-empty list whose entry's own text is blank means "found, and confirmed empty" — these are two different real document states this function (and every checker built on it) is careful never to collapse into one answer.
2. **`_page_for_offset(fields, offset)`** — maps a character offset in `fields["full_text"]` back to a real page number, by walking `fields["pages"]` (one dict per real PDF page, built directly from `pypdf` extraction, 1-indexed). This is how almost every checker below turns "I found this text" into "cite this page."
3. **`_goal_block_starts(text)`** — splits the document into per-goal blocks, delimited by either `Target Goal:` (skill-acquisition goals) or `Target Name:` (Behavior Reduction / BIP goals) — a single shared block-splitting convention used by a large fraction of the Goals-in-Progress/BIP rules below.
4. **The escalation path**: every deterministic checker returns `(result, evidence, page, confidence)`. If `confidence < 0.6` (`fields.py::ESCALATION_CONFIDENCE_THRESHOLD`), the finding is escalated — the SAME rule_id is also sent to the judgment layer in the same batch, and **the judgment layer's result wins** in the final merged output (the deterministic attempt is kept alongside as `det_attempt`, visible for debugging, but never shown to a reviewer as the final answer). This means a "deterministic" rule can still end up judgment-decided on a given document if its own checker can't confidently resolve it — this is by design, not a bug, but it means a deterministic rule's real, final behavior on a hard case still depends on the judgment layer (see `JUDGMENT_RULES_REFERENCE.md`'s own escalation section).
5. **Page-citation shape**: `page` is either a single `int`, a `list[int]` (a finding that genuinely spans several specific pages), or `None` (genuinely nothing to cite — e.g. a whole-document "not found anywhere" claim). `evidence` can be a plain string, or (for a true multi-page, per-page-distinct finding) a list of `{"page": int, "detail": str}` objects, one per page.

## Known structural fragile patterns — confirmed real, not theoretical

These are patterns **directly confirmed as real bugs this project has hit more than once**, across different documents, in different rules — flagged here as a class, not just a one-off fix, since the same shape can resurface in a rule not yet tested against a document that happens to use it.

1. **"Label on one line, value on the next line."** Several real documents place a field's value on the line *after* its own label (`"Behavior: \nAggression"`, `"Name of Skill:\n<sentence>"`) rather than on the same line. A regex written as `Label:[ \t]*([^\n]+)` (same-line-only) silently finds nothing on these documents — not a crash, not an error, just a quiet `None`/`[]` that looks identical to "this field is genuinely absent." Confirmed real instances: `_check_BIP08`'s `"Behavior:"` extraction (Round 19), `_extract_mastered_goals_with_dates`'s `"Name of Skill:"` extraction (Round 19, the most serious bug found that round — see below), and others earlier in this project's history (`_check_MAST03`'s own docstring documents the same class for `"Additional Notes:"`).
2. **"First match only, not every match."** A checker that does `re.search(...)` (first match) instead of `re.finditer(...)` (every match) when a document can genuinely have the fact in question stated more than once, or that only cites the *first* occurrence's page when every occurrence is relevant to the finding. Confirmed real: `QA-TEMP-01`'s original fail branch cited only the first of several real contradicting credential mentions (Round 15); `_check_BIP06`'s pass branch cited only the first of multiple passing Behavior Reduction goals (Round 19).
3. **"First match in the WHOLE document, not the relevant section."** A keyword/phrase search run against the *entire* `full_text` can match an unrelated, out-of-context occurrence earlier in the document (e.g. an early-childhood history sentence) before it ever reaches the real, relevant content the rule is actually about. Confirmed real: `QA-SCH-06`'s original regex matched a bare "speech-language" mention in a Biopsychosocial history paragraph, picking page 4, when the real, relevant Educational-History content was on page 5 (Round 18) — fixed by requiring a nearby frequency/schedule anchor rather than a bare keyword.
4. **"A restatement/cross-reference section re-lists names already counted."** A document section that exists purely as a cross-reference (e.g. `"Community Goals:"` re-listing goal names already counted in the main Goals-in-Progress section, purely to flag which ones are worked on in community) can silently double-count if a counting checker has no section boundary. Confirmed real: `QA-GIP-13`'s original goal count was inflated by exactly this (Round 19) — three separate judgment-layer votes on the SAME real document had each guessed a different, wrong count, and the real fix was a deterministic, bounded count, not more voting.
5. **A spelling variant of the same real-world fact.** A document can spell the same behavior two different ways in two different sections (`"Aggression"` in one place, `"Agression"` in another) — a real, confirmed typo in the source document, not a bug in extraction. An exact-string keyword match then treats these as two different facts. `pipeline/fields.py::_fold_doubled_letters`/`_text_contains_behavior_name` (Round 19) exist specifically to tolerate this one narrow, confirmed-common typo class (a missing/extra doubled letter) without weakening matching enough to produce false positives on a genuinely different word.

**These patterns are confirmed in the specific rules named above. They have not been independently re-verified against every other rule in the table below — a rule not mentioned here may still share one of these same fragile shapes on a document that happens to trigger it. This is stated plainly rather than silently assumed fixed everywhere.**
